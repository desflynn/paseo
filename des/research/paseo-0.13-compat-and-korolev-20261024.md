## 0. Verdict

**Paseo 0.13.0 is safe for our plugins and for dci-harness, needs a re-carry of six of our overlays, and gives Korolev a station-down control link but not a grant, registry or roll-up.** Nothing we run is removed. No upgrade, install, reload or restart was done. Everything here is a read of `/tmp/paseo-v013` plus one `git apply --check` run.

- **Safe, no change needed before upgrade:** paseo-progress plugin (PP), dci-harness and dci-mcp (DCI Head Guy), the seat, launch, instruct, labels, schedule and heartbeat paths DCI uses.
- **Needs a change, nothing breaks:** semantic renderer plugin (PSR): migrate 10 imports from `@getpaseo/plugin/client/react-native` to `client/ui`. The old path works until after 2027-04-20. PP has the same deprecation on about 30 files.
- **Our fork needs work:** 6 of our 13 overlays do not apply to vanilla 0.13 and must be re-carried (mine-label, sub-label, reload-wait, speak-all-sessions, pi-compaction-status, unsigned-macos-build). 6 apply clean. acp-context-meter was already retired in 0.12.
- **Two behaviour changes to know about, both cosmetic for us:** an agent's `send_agent_prompt` and `paseo agent send` now return a queued receipt and deliver after two quiet seconds; `create_agent` no longer creates worktrees (use `create_workspace` first). DCI does not use the removed path.
- **Canary first.** The Claude and Pi provider code changed a lot (claude `agent.ts` +539 lines) and nobody has read it for effects on our hooks, MCP injection or env. One canary seat on a throwaway 0.13 daemon, then the fleet.
- **Korolev:** see section 3. Short form: use connected hosts as the station-down control plane; keep grants, registry, reporting-up and credentials in our own layers.

## 3. Korolev and cross-host (state: DONE, written from my own source read of `/tmp/paseo-v013`)

Sources read in full: `docs/connected-hosts.md`, `docs/permissions.md`, `docs/relay-endpoint-security.md`, `connected-hosts/{index,link,session}.ts`, `agent/host-operations/index.ts`, the host-routing wrapper in `agent/tools/paseo-tools.ts:741-800`, `session-admission-auth.ts`, `protocol/src/hosts.ts`. Not read: the app UI side (Subagents track across hosts), the client SDK `hosts` module, the relay server. Those are NOTES only.

### 3.1 Short answer for Korolev

0.13 gives Korolev a **working one-hop control link from one daemon to another**, and an MCP surface that lets an agent on A **start and watch work on B**. It does not give Korolev **identity, grants, a registry or a roll-up**. Those stay Korolev's to build, and 0.13 sets the ceiling they sit on.

### 3.2 How host A reaches host B (SOURCE)

| Question           | Answer                                                                                                                                                                                                                                                                                      | Evidence                               |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------- |
| Who holds the link | A stores B as a saved "connected host" in A's own `hosts.json` (0600, atomic write). Saved hosts belong to the daemon, not the app's connection list.                                                                                                                                       | docs/connected-hosts.md:5-14           |
| Transport          | A connection string: TCP `host:port`, `ws://`/`wss://`, local socket or Windows pipe, **SSH** (fresh ssh process per attempt, reaching an already-running daemon), or a **relay pairing offer URL**.                                                                                        | public-docs/cli.md:83                  |
| Auth               | The credential in the connection string (daemon password, or the pairing offer). B treats every admitted link as principal `owner` with all nine permissions.                                                                                                                               | session-admission-auth.ts:15-31        |
| Discovery          | **None automatic.** Each host is added by hand (`paseo --host A host add <conn>`). `list_hosts` lists only what A has saved.                                                                                                                                                                | connected-hosts/index.ts; docs         |
| Identity           | B's `serverId` is learned on first connect and **pinned**. A changed identity is refused (`server_id_mismatch`) until an explicit `--replace-identity`. Self and duplicate registrations are flagged.                                                                                       | connected-hosts/index.ts:269-330, ~430 |
| Encryption         | Direct and SSH: whatever the transport gives (plain ws is cleartext). **Relay: end-to-end** `Noise_NK_25519_ChaChaPoly_SHA256` using the existing `daemon-keypair.json`, replay-protected; the legacy NaCl-box mode is still accepted unless `daemon.relay.requireProtectedSecurity` is on. | docs/relay-endpoint-security.md        |
| Shape              | One authenticated physical link per saved host, **multiplexed into isolated virtual sessions** (`hosts.link.open`, `hosts.route.*`). Caps: 128 channels per link, 128 routes, 32 per caller, 64 MiB output. **One hop only.** Saving a host grants B no access to A.                        | link.ts:65-80, session.ts:62-70        |
| Failure            | Unreachable hosts stay saved and retry with capped backoff. A wrong password stops retries (`authentication_failed`). A lost response surfaces as `DAEMON_CONNECTION_LOST` with `outcome:"unknown"`; **mutations are not replayed**.                                                        | connected-hosts/index.ts:330-345       |

### 3.3 What an agent on A can do on B (SOURCE: `hostTools` map, paseo-tools.ts:~728)

Seven MCP tools gained an optional `serverId` (from `list_hosts`): `create_workspace`, `list_workspaces`, `create_agent`, `send_agent_prompt`, `get_agent_status`, `get_agent_activity`, `list_agents`.

| Wanted                                             | Cross-host in 0.13?                                                                                                                                                                                             |
| -------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Launch an agent in a workspace on B                | **Yes, with limits.** The workspace must already exist on B (make it with `create_workspace` + `serverId`); provider and model must be explicit; local filesystem defaults do not apply.                        |
| Create a workspace on B                            | **Yes.**                                                                                                                                                                                                        |
| Message an agent on B                              | **Yes.** Returns a **queued receipt**, not "turn started"; delivery follows two quiet seconds later. Agent callers default to `steer`.                                                                          |
| List agents and workspaces on B                    | **Yes**; no caller-directory default, so pass `cwd` to filter.                                                                                                                                                  |
| Read status and activity                           | **Yes.**                                                                                                                                                                                                        |
| Wait for a B agent                                 | **Indirectly.** No wait tool. A's daemon keeps a durable finish subscription and notifies the caller on finish, error or permission. Three failed observation attempts end it with "status unknown".            |
| Cancel, archive, kill, rename or retitle a B agent | **No, not from the agent MCP surface.** `cancel_agent`, `archive_agent`, `kill_agent`, `update_agent`, `set_agent_mode`, permission responses, schedules, heartbeats, terminals and `speak` take no `serverId`. |

NOT CONFIRMED: whether a script using the routed SDK/CLI path (`paseo.hosts`) can cancel or archive on B. A routed session carries the caller's grants, so probably yes, but I did not read `packages/client/src/hosts`.

### 3.4 Workspaces, labels, parent/child, permissions across hosts

- **Workspaces:** each lives on exactly one daemon. A remote create needs B's `workspaceId`. No cross-host workspace object. `projectKey` is per daemon, merged by the app as before.
- **Parent/child:** a remote child gets `parentAddressLabels({agentId, serverId})` plus `paseo.parent-server-id` (new), so B knows its parent is on A. The parent's Subagents track shows children across hosts (NOTES, UI side).
- **Our MINE/SUB overlays:** they key on `paseo.parent-agent-id`. A child on B whose parent is on A carries that id plus the server id, so B's overlay could paint SUB with a parent it cannot find. NOT CONFIRMED; needs a live test.
- **Permissions are the weak spot.** A password, a local credential or no password all map to principal `owner` with all nine permissions. Daemon-wide, no scoped principals. MCP cross-host calls are sent with `OWNER_PERMISSIONS` (host-operations/index.ts:99), "bounded by the destination's admission of its link". So **a link to B is a full-owner link to B**. The one narrowing: a caller with `lockedCwd` cannot use any remote host. The permissions doc says workspace-scoped grants are future work.
- **Secrets:** the connection string, password included, sits in A's `hosts.json` at 0600; replacement input never returns through a read API. The 0.12 issue still holds: agents inherit the daemon's env, so never put the password in the daemon env.

### 3.5 What is still missing or fragile

1. **No per-seat or per-agent authority across hosts.** All-or-nothing owner. "Seating is a grant" has nothing in Paseo to attach to.
2. **No cancel/archive/kill/mode/permission-response from the agent surface** on a remote host. A parent can start and watch a remote child but cannot stop it.
3. **No discovery or registration.** Every link is added by hand, per host, per direction; N hosts means N(N-1) links. Saving A on B does not give B reach to A.
4. **One hop.** Station to surface works; station to surface to sub-surface does not.
5. **`send_agent_prompt` is fire-and-queue.** The caller cannot know the turn started. Observation rests on the daemon-held subscription and its three-strikes rule.
6. **Mutations are not replayed.** A failed local write after a successful remote create leaves a child nobody watches (the docs say so).
7. **Plain `ws://` and TCP are cleartext.** Fine over Tailscale; elsewhere use `wss`, SSH or relay.
8. **Cross-host label semantics for our overlays are untested** (3.4).
9. **Version coupling.** Both daemons must advertise `connectedHosts` (and `hostMultiplexing` for the shared link). An older daemon is refused with "Update the destination daemon". Every machine needs 0.13 before it can be a link target, so our -df overlays must be carried to 0.13 first.

### 3.6 Fit with the station-and-surface layout

- **Station to surface control fits well.** Korolev's Paseo holds one saved host per surface (MS, DGX, IDP, PCG5). Its seats use `list_hosts`, `create_workspace`, `create_agent`, `send_agent_prompt`, `list_agents` and `get_agent_status` with `serverId`. That is the "ask goes down" half of the chain, built in.
- **Surface to station (reports up) is not served.** The link is initiated by A. A surface would need a saved host pointing at the station, giving each side owner authority over the other. "Board state only, up" cannot be enforced by Paseo; it stays a convention or Korolev's own channel.
- **Relaying down through the station** becomes unnecessary for launch, message, list and status. It stays for cargo, memory, board roll-up and anything Paseo does not carry.

### 3.8 Recommendation

Use 0.13 connected hosts as the **station-down control plane** (launch, message, list, status). Do not build the grant, registry, report-up or credential pieces on it. Before relying on it: (a) live-test between two throwaway daemons on one Mac, including `mine-label`/`sub-label` and `send --behavior steer`; (b) decide what the saved-host password is and who rotates it, since a link is full owner; (c) read the client SDK `hosts` module to settle cancel/archive.
